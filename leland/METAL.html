Training the Microduck on Apple GPUs: my first open-source project

Started 2026-11-03. Goal: make Pollen's real Microduck training run well on Apple Silicon Macs, by joining and helping an existing community effort. Claude does the engineering; I'm the maintainer: I decide, review, and put my name on what goes out.

Why this is hard (the short version)

Pollen's training runs 4,096 ducks at once on an NVIDIA graphics card. Everything in it already runs on a Mac except the physics engine, which is written in NVIDIA's own GPU language:

Layer What it does On Apple's GPU?
PyTorch the duck's brain and the learning maths ✅ yes (Apple's "MPS")
rsl_rl the PPO learning loop ✅ yes (plain PyTorch)
mjlab the duck's world: rewards, curriculum, randomisation ⚠️ needs small changes
MuJoCo Warp the physics, thousands of ducks in parallel ❌ NVIDIA only (written in Warp → CUDA)

A full rewrite would be months of expert GPU work. But someone has already started.

What already exists (found 2026-11-03)

  • warp-metal by David Dobas (innate-inc), Apache-2.0, started September 2026. It adds an Apple GPU device (metal:0) to NVIDIA's Warp, so Warp's GPU code compiles to Apple's Metal instead of CUDA. Install: pip install warp-metal next to warp-lang 1.17.0. Needs macOS 15+.
  • With two small patches to MuJoCo Warp and mjlab (his forks, branches metal-3.11 and metal, PRs open), Pollen's framework runs on it.
  • DavidDobas/microduck_rl, branch metal: the Microduck on a Mac. Just 4 files changed. It also moves from mjlab 1.3.0 (what Pollen uses) to mjlab 1.6.0, so results aren't a pure like-for-like comparison with Pollen's.
  • His speed figure: a humanoid robot (Unitree G1) with 1,024 environments takes about 1.0 s per learning round on an M5 Pro, against 0.3 s on an RTX 5090. Apple falls further behind with more environments (GPU threadgroup memory).
  • Known limits: Apple GPUs have no 64-bit floating point; some atomic operations aren't truly atomic; Apple's compiler can miscompile big unrolled matrix maths.
  • Hardly anyone has noticed it yet (1 star when I found it). Other attempts are narrower: MJX on jax-metal (reported broken), MLX ports (RobotFlow-Labs, lucidrains).

2026-11-04: found a bug: stand-up ducks fall through the floor

Trained Mjlab-StandUp-Flat-MicroDuck for 750 rounds on the Studio overnight (48 min 42 s). In the report-card video (TRAINING.md §13), the ducks that failed had sunk through the floor. I listed which robot parts can touch the floor in the compiled model:

Task Pollen's original (mjlab 1.3) Metal branch (mjlab 1.6)
Walking (robot_walk.xml) the 2 feet the 2 feet ✅ same
Stand-up (robot_groundcontact.xml) 10 parts: trunk, hips, legs, jaw, feet only the 2 feet ❌

Cause: in the ground-contact model, the body-contact geoms have no names. Both versions apply FULL_COLLISION (pattern .*_collision) with disable_other_geoms=True. mjlab 1.3 disabled the others by name (spec.geom(name)), so unnamed geoms slipped through and kept their contact, by accident. mjlab 1.6 loops over the geom objects themselves, so it correctly switches off every unmatched geom, unnamed ones included. David's contype=1, conaffinity=1 change only covers the matched (named) geoms.

Affects every task that uses the ground-contact models: stand-up, sit-stand, ground pick, roulade, rollers. Doesn't affect walking (velocity), so the Studio walking result stands. Pollen hits it too the day they move to mjlab ≥ 1.4.

Possible fixes (David's or Pollen's call): give the ground-contact geoms names that match the rule (e.g. trunk_collision), or set disable_other_geoms=False on the ground-contact robot's CollisionCfg. Either way, check it with the same parts list.
